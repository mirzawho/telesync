# Asynchronous full replacement of a Telegram channel message

## A. Metadata

See frontmatter. The user confirmed continuation in the turn following this
handoff; this is recorded as approval for this task.

## B. Requirements

### Problem

There is no API for changing an existing Telegram channel message. The gateway
currently serves history reads, deletion, copying and asynchronous direct sends;
the worker contract has `SendMessage` but no edit operation. Direct Send cannot
implement editing because it creates a new Telegram message and its durable
operation identifies a destination but no target message.

### Desired behavior

- `PUT /api/v1/telegram/{key}/channels/{channel_id}/messages/{message_id}`
  accepts a complete replacement state, preserves the target message ID and
  performs the operation asynchronously.
- JSON replaces text/entities and requests no media; multipart `payload` plus
  one `file` replaces text/entities and media. Omitted/empty media never means
  “keep the old attachment”. Empty text is valid only with new media.
- The background operation uses Telegram's native `messages.editMessage` on
  the selected connection and the resolved channel `InputPeer`. It never sends
  a second message or deletes/recreates the target.
- Accepted operations are durable, idempotent, recoverable and pollable through
  `GET /api/v1/telegram/{key}/channels/{channel_id}/messages/{message_id}/edit/{operation_id}`.
- The final message state is verified. Unsupported media removal/transitions,
  albums and authorization failures are reported explicitly; old content is
  never reported as replaced when the remote state does not match.

### Acceptance criteria

- [x] PUT route validates positive channel and message IDs, authenticates,
  applies channel visibility and the approved application-level edit
  permission, and returns 202 only after staging, persistence and enqueue.
- [x] JSON and multipart payload validation enforces the full-replacement
  contract, reusable staging limits/sniffing, one file, and entity bounds.
- [x] A distinct durable edit operation/job supports status polling, idempotency
  conflict handling, restart/lease recovery, retention and safe retry/unknown
  outcomes; same-target edits serialize without blocking other targets.
- [x] Worker RPC and gotd use the target connection and native edit method,
  preserve the message ID and replacement text/entities/media, and never call a
  send/delete workaround.
- [x] Supported text/media transitions are verified; unsupported removal,
  album edits and server refusals fail honestly. A no-op is recognized only
  after checking the resulting remote state.
- [x] Operation status is read-only and scoped to principal, connection,
  channel and target message. The bearer token is not persisted.
- [x] API routes, generated docs and manual semantics are synchronized using
  the docs generator. Focused tests, docs checks, regression and build checks
  pass; live Telegram verification is reported separately.

### Out of scope

- Editing albums as a group or changing sibling messages.
- Triggering workflow/webhook events for edits.
- A partial-update or `keep_existing` media mode.
- Deleting and reposting messages as a fallback.
- Live changes to production Telegram messages without an explicitly
  authorized test target.

### Symbols and contracts

- `Server.message(...)` validates positive IDs, checks `requireChannelView`,
  then calls `Worker.Message`; it only serves the existing read operation.
- `Server.sendTelegramMessage(...)` gates on `content.publish`, resolves the
  destination through the local channel row for `visibleChannel`, parses JSON
  or multipart, then accepts work through `sending.Service` and returns 202.
- `sending.Service.Accept(...)` validates direct-send payloads, durably stages
  media, fingerprints content, records `SendOperation`, enqueues a durable send
  job, and removes staged files if acceptance fails.
- `sending.Service.Execute(...)` claims the send operation, reads staged media,
  calls `publishing.DirectResult`/`Worker.SendMessage`, records completion or
  failure, and has send-specific recovery semantics including persisted
  Telegram `random_id`.
- `rpc.Backend` and `worker.Telegram` expose `SendMessage` as their only content
  write today. `gotdclient.Manager.SendMessage` calls
  `api.MessagesSendMessage`; there is no edit RPC or gotd call in the graph.
- `tgapi.NormalizePermissions` already carries an `Edit` channel capability
  from Telegram admin rights, but it is not a per-message author/age guarantee.
  Telegram remains authoritative for the exact target.
- `internal/apidocs/table.go` is the hand-maintained route table. Generated
  pages must come from `go run ./cmd/docsgen`, never manual edits.

### Dependencies and call paths

- Existing send path: HTTP gateway → `sending.Service.Accept` → staging +
  `message_send_operations` + `telegram_message_send` job → queue handler →
  `publishing.DirectSend` → worker RPC → gotd `MessagesSendMessage`.
- Proposed edit path: HTTP PUT → edit-specific validation/authorization →
  shared durable staging + distinct edit operation/job → queue handler →
  selected worker's edit RPC → gotd `MessagesEditMessage` → verify by reading
  the same channel/message → record terminal operation. No path may invoke
  `SendMessage` or delete/recreate.
- Message reads are fetched live through the selected worker. The repository's
  documented architecture says messages are not stored locally, so a local
  content-cache reconciliation step is not currently evidenced as necessary.

### Unknowns / risks

- **Application edit permission — resolved for implementation:** use the
  existing `Authorizer.Allowed(KindChannel, ActionUpdate, managedChannelID)`
  grant after `visibleChannel`. It applies the current administrator/manage
  scope and explicit per-channel allow/deny rules, and does not reuse
  `content.publish`. Telegram `Permissions.Edit` and the target-specific
  author/age rules remain separate remote checks.
- **Native media removal:** verify installed gotd types and Telegram's support
  for explicit `InputMediaEmpty` on `messages.editMessage`; otherwise return
  `edit_media_removal_unsupported` for media-to-text. Do not claim support from
  the constructor's existence alone.
- **Cross-kind media transitions and albums:** behavior is destination/server
  dependent. Verify native edit semantics and reject unsupported transitions;
  never split/recreate an album.
- **Edit retries:** unlike send, edits do not have the existing persisted
  `random_id` idempotency contract. Resolve retries by reading back the exact
  target and comparing the requested state; use terminal `unknown` when safe
  confirmation is impossible.
- **Per-target locking:** the shared queue serializes by `(job_type,target_id)`;
  determine a safe durable target key for `(connection, channel, message)` so
  same-message edit ordering does not serialize unrelated messages.
- **Background authorization principal:** persist principal identity and
  revalidate current permissions while avoiding bearer token persistence.
- **No local cache:** confirm there is no additional cache outside the current
  live message-read path before claiming cache invalidation is complete.
- **Backend behavior:** actual MTProto rights and transition support require a
  controlled authorized account to verify live; fakes prove request shape only.

## J. Implementation result

The asynchronous full-replacement API is implemented at
`PUT /api/v1/telegram/{key}/channels/{channel_id}/messages/{message_id}` with
read-only polling at
`GET /api/v1/telegram/{key}/channels/{channel_id}/messages/{message_id}/edit/{operation_id}`.
It records an edit-specific durable operation and queue job, stages attachments
with the shared staging area, scopes idempotency to the principal and request,
rechecks channel `ActionUpdate` before execution, then calls native
`messages.editMessage` on the selected connection and verifies the same target
message ID by readback. It has no send/delete fallback. Startup cleanup preserves
attachments held by either send or edit operations.

**Verified:** `go test ./...`, `go build ./...`, `go vet ./...`,
`go run ./cmd/docsgen --check`, `go test ./internal/apidocs`, and
`git diff --check` all pass. `gofmt -l` on the changed feature packages and
files is empty. A repository-wide `gofmt -l .` also reports the existing
unrelated `.claude/worktrees/full-message-replacement-api-b6e9bd/internal/rpc/rpc.go`;
it was not changed as part of this handoff.

**Telegram behavior limits:** text-only replacements and an uploaded voice
replacement are covered by the fake MTProto server. Media-to-text uses explicit
`InputMediaEmpty`; Telegram media-removal refusal codes and grouped-media
refusals map to explicit unsupported errors, and successful removal requires
readback with no media. Live backend support, account rights and edit-window
behavior remain unverified. No live Telegram/Cat request was made.

The concurrent, separately approved message-delete handoff and Graphify changes
remain in the shared worktree; this handoff does not report its status.
