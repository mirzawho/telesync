# Redesign channel information dialog as a Persian RTL profile

## A. Metadata

This handoff scopes the existing Channel Information Dialog only. Explicit user
approval naming this handoff was received on 2026-11-11.

## B. Requirements

### Problem

`channel-information-dialog.tsx` currently renders a small title, a size-20
avatar URL, and a vertical list of metadata. It lacks the requested profile
hierarchy, large avatar/fallback, real actions, and grouped public details.

### Desired behavior

- Present the selected row's actual channel detail in a centered Persian RTL
  profile: prominent avatar/title, real verification and participant count,
  supported action tiles, separate link/description content, and collapsed
  `اطلاعات بیشتر` for secondary metadata/permissions.
- Reuse the existing Dialog, detail request, authenticated avatar mechanism,
  toast, routes, design tokens, and existing supported actions. Keep stale
  request cancellation and loading/error behavior; never mix local row ID with
  remote Telegram ID.
- Omit unsupported actions and unavailable values. Do not fabricate links,
  counts, permissions, or Telegram operations.

### Acceptance criteria

- [x] Profile-style muted header, large real/fallback avatar, centered title,
  conditionally verified/scam/fake status, and only a real count.
- [x] Equal RTL-friendly tiles for supported actions only; copy ID uses remote
  `detail.id`, View uses the local row ID route and read permission, and no
  invented mute/gift/leave actions.
- [x] Public link appears only when authoritative and valid; description remains
  readable with paragraph breaks; metadata and actual permissions are in a
  collapsed `اطلاعات بیشتر` Accordion.
- [x] Loading/error states remain; stale fetches are canceled; changing rows
  never briefly displays previous channel data.
- [x] Focused tests cover profile content, fallback/count/link boundaries,
  verified state, actions/identities, details accordion, loading/error and row
  identity; frontend typecheck and production build pass.
- [x] No unrelated explorer, message, publishing, backend, or API changes.

### Out of scope

- Channel creation/join APIs and dialogs, list/search/categories, message UI,
  publishing, backend contracts/permissions, global layout, dependencies,
  browser or live Telegram actions.

### Unknowns / risks

  read permission. To implement View and authenticated avatar safely, pass the

  no permissions object; the dialog's fetched detail does.

## D. Implementation plan

1. **`channel-information-dialog.tsx`** — retain the request effect and error
   handling; restructure the same Dialog as a responsive RTL profile with a
   header, large authenticated avatar/fallback, prominent data and Skeleton.

   existing message route destination as needed; preserve remote-ID detail
   fetch. Gate View with actual read permission from fetched detail.
3. **`channel-information-dialog.tsx`** — use existing Button, DropdownMenu,
   Accordion, Lucide icons and `useToast` for only supported copy/view actions;
   group real link/description and secondary metadata. Never infer custom links.
4. **Focused tests** — extend dialog SSR tests and, where necessary, add
   testable pure view logic for count/URL/permission/identity boundaries. Keep
   `channel-list.tsx` behavior unchanged and test row → dialog identity if the
   existing test seam allows it.
5. **Validation** — run panel tests, frontend typecheck and production build;
   inspect `git diff --check`. No browser claim unless browser verification is
   actually available and performed.

### Must not change

- Backend/API/contracts, channel creation/join, channel list/search/category
  behavior, messages, publishing, automation, dependencies, or global layout.
- Do not use a local ID as remote ID or the reverse; do not pass remote ID to
  `ChannelAvatar`.

Implemented the existing dialog as a responsive RTL profile with authenticated
local-avatar loading/fallback, real title/count/verification/warnings, permission-

omitted rather than guessed or leaked. There is no browser automation in this
workflow; browser and live-channel verification were not performed.
