# Use the shared chat composer for message editing

## A. Metadata

Prepared under the required test-first workflow. No production implementation has started.

## B. Requirements

### Problem

The active message pane renders `ChannelMessageEdit` in a separate footer when editing. That component contains its own textarea, large bordered form, three media radio actions, native visible file control, media Select, and separate Save/Cancel row. Meanwhile `ChannelMessageComposer` is the compact send composer with the existing attachment Sheet. The two independent forms create the rejected duplicate/oversized editing experience.

### Desired behavior

- Keep exactly one mounted `ChannelMessageComposer` and one textarea.
- Switch that composer between Send and Edit modes, prefilling edit text and showing a compact context strip, cancel affordance, existing media preview, and one Save action.
- Preserve the normal send draft across edit entry/cancel; do not cross-submit text/media to a different target.
- Reuse the same attachment Sheet and represent media keep/replace/remove as draft state, not radio buttons.
- Reuse existing PUT, idempotency, polling and history refresh behavior; show progress on the existing target message and update the original bubble only after confirmed status.
- Preserve permissions, timeline identity, existing message ID, scroll anchoring, send flow, delete and publish actions.

### Acceptance criteria

- [ ] Old full-height `ChannelMessageEdit` form is no longer rendered or used.
- [ ] One shared composer renders in both modes, with one textarea, attachment action and primary action.
- [ ] Edit context is compact, previews original text/media, supports cancel, and focuses/prefills the shared textarea.
- [ ] Send draft is restored on cancel; switching edit targets cannot lose drafts or mismatch message IDs.
- [ ] Existing media defaults to keep; replacement uses the shared Bottom Sheet and existing multipart fields; removal stays explicit until Save.
- [ ] Existing API's `keep_media` behavior is preserved for caption-only edits; no ambiguous `media: null` is sent.
- [ ] 202 remains pending; confirmed status refreshes and replaces the same message ID; failure preserves original message and edit draft; unknown outcome does not auto-retry.
- [ ] Existing send/paging/scroll/permission/edit/delete/publish regressions pass.
- [ ] Typecheck/build pass; browser verification is recorded honestly.

### Out of scope

- Backend API redesign, new routes/dialogs, changes to Send/Delete/Publish behavior, broad Channel Explorer redesign, or new UI dependencies.

### Symbols and contracts

- `ChannelMessagesPane.beginEdit(message)` currently sets target state but has no path to seed the composer draft.
- `ChannelMessagesPane.saveEdit({text, mediaAction, file, mediaKind})` maps `keep` with existing non-webpage media to `{keep_media:true}`; `replace` to `{media:{kind}}` plus multipart file; `remove` leaves both absent, the backend's current explicit remove semantics. It polls `getEditOperation(client, channel.id, target.id, operation_id)` and validates returned `target` identity.
- On `edited`, it calls `refreshLoaded(target.id)` and `replaceMessage(fresh)`; existing operation progress is passed to the target's `ChannelMessageItem`.
- `ChannelMessageComposer` currently owns its local text/file/media state and receives `onSubmit`; accepted Send clears its local draft.
- Existing panel tests use static server rendering, not a DOM interaction framework. Interactive transitions need tests via pure state seams or existing test harness patterns; do not claim browser-like behavior from static rendering alone.

### Dependencies and call paths

- Message action `onEdit` → pane `beginEdit(message)` → pane currently removes normal composer and mounts separate `ChannelMessageEdit`.
- Old editor submit → `saveEdit` → typed `editChannelMessage()` PUT → `getEditOperation()` polling → `refreshLoaded()`/`replaceMessage()` → same timeline message ID updates.
- Send path remains `ChannelMessageComposer` → `send()` and must remain intact when mode switching is added.
