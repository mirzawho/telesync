# Channel Explorer server multi-select

## A. Metadata

Preparation only. The owner approved the existing design and requests a compact server selector in the category-chip toolbar, physically right of the chips under RTL. No production code is changed in this handoff.

## B. Requirements

### Problem

`web/apps/web/app/routes/_panel/channels.tsx` currently resolves one `server` from the `?server=` query (falling back to the first server), but the server is not applied to the local channel list. The existing channel-list toolbar has search followed by a standalone category-chip row.

### Desired behavior

- No `server` query parameter means all eligible configured servers. A single value remains compatible; repeated values select a union. Deduplicate and ignore invalid query keys, preserving valid offline keys where the available connection list permits.
- Use configured connection keys, never display names or channel IDs. Search AND category AND server filters apply client-side to the existing fully fetched local list (currently `listAll` capped at 5×100).
- Selector remains fixed while category chips scroll horizontally in one compact row; under RTL selector is physically right of categories. Preserve current sidebar width and other UI.
- Trigger summaries: all servers, real display name for one, localized count for multiple. Popover supports searching, accessible checkbox multi-selection, immediate updates, and all/reset normalization. No fake `all` API key.
- Synchronize repeated `server` params without losing unrelated query state; selected channel links retain these params. Do not remount the message child unnecessarily. If selected channel is excluded, route to unselected explorer state, never a random channel.
- Server loading/error/empty configuration is distinguishable from all-server success; never treat API failure as a successful empty server list.

### Acceptance criteria

- [ ] All/single/multiple selection, removal-last normalization, deduplication, trigger summaries.
- [ ] Server/category/search filters compose and preserve composite channel identity (`client_key` + Telegram id/local record identity as appropriate).
- [ ] URL initialization, repeated params, updates, unrelated params, Back/Forward and channel navigation are covered.
- [ ] Selected channel remains if included and clears safely if excluded.
- [ ] Accessible searchable dropdown, physical RTL placement, single row, category scrolling retained.
- [ ] Focused tests, typecheck, relevant tests, production build pass; browser visual verification only if a real session is available.

### Out of scope

No backend/API rewrite unless the inspected listing contract proves necessary; no changes to channel creation, joins, dialogs, row menus, message viewer, navigation, automation, webhooks, or connection management.

### Symbols and contracts

- `clientLoader({request})`: GET `/telegram` returns `{servers: TelegramServer[]}`; local list fetched through `listAll<Channel>(..., "/local/channels", ..., {}, LIST_PAGES)` with `LIST_PAGES=5`.
- `shouldRevalidate`: returns true only for form submissions; URL filter edits currently do not reload the loader.
- `ChannelListPane`: owns search/category toolbar rendering, receives filtered channel rows and category state.
- `filterChannels(channels, {search, categoryIds, filed})`: pure client-side filtering; currently ANDs search with category (any selected category match).
- `Channel.client_key` identifies the Telegram connection; list row key and current selection use local `Channel.id`.
- `TelegramServerCombobox` and create/join flows get connection choices from `/telegram`; names/keys must remain distinct.

### Dependencies and call paths

- Route loader → `requireSession` → `GET /telegram` + `listAll /local/channels` → route component filters in memory → `ChannelListPane` renders.
- `ChannelListItem` reads `useSearchParams()` and puts the whole current query in channel-link navigation, so repeated server params can naturally survive selection.
- Category memberships are fetched category-by-category into `filed: Record<number, number[]>`, keyed by local managed-channel id.
