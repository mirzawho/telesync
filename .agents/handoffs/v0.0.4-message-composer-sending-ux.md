# Telesync message composer and sending UX redesign

## A. Metadata

This is a preparation handoff. Project policy requires explicit approval naming this handoff before production implementation.

## B. Requirements

### Problem

`ChannelMessagesPane` renders send-operation statuses in a separate footer, including a successful-send label, and also writes a success notice after a sent operation. The composer is a form with a media-kind `<select>` plus a separate hidden file input and attachment label.

### Desired behavior

- HTTP 202 acceptance clears the active draft and creates a private-content-free pending bubble in the message timeline.
- Poll operation status using the accepted operation identity and channel connection. Do not create a success toast or success footer.
- On `sent`, refresh actual message history and remove the pending bubble only when the real server message is present; retry bounded refresh on eventual consistency.
- Keep failures/unknown outcomes isolated per operation and provide safe draft recovery without automatic resubmission or fresh idempotency identity.
- Support an unbounded-in-practice list of independent pending operations (no arbitrary five-item truncation) without mixing channel identities.
- Replace the media Select + attachment button with one accessible Paperclip opening a bottom Drawer with Photo, Video, Audio, Voice, Document actions and compatible file pickers.
- Preserve selected file/media semantics on cancellation, preview/remove behavior, draft text, permission checks, destination identity, existing timeline scrolling and message management.

### Acceptance criteria

- [ ] No successful new-send toast, footer label, or notice.
- [ ] A subtle in-timeline pending bubble never exposes draft text/media and is separate from Telegram message data.
- [ ] Accepted sends reconcile against a real history result; bounded eventual-consistency retries and terminal handling prevent indefinite polling.
- [ ] Failed/unknown operations preserve recoverable drafts; unknown does not automatically resend.
- [ ] Concurrent pending sends remain independent and channel-scoped.
- [ ] A Paperclip bottom Drawer directly opens the correctly filtered file picker for all five media kinds.
- [ ] Picker cancellation preserves an existing attachment and creates no empty selection.
- [ ] Textarea, previews, responsive RTL layout, IME/Enter behavior and permission guards remain correct.
- [ ] Relevant tests, web typecheck, production build, and browser checks are recorded honestly.

### Out of scope

- Backend/API contract changes, global toast changes, recording audio, unrelated Channel Explorer redesign, and changes to edit/delete/publish behavior.

### Symbols and contracts

- `ChannelMessagesPane.send()` submits through `sendChannelMessage(client, channel.id, payload, idempotencyKey, ...)`; it validates accepted `client_key` and remote `channel_id` against current identity.
- `getSendOperation(client, channel.id, operation_id, ...)` polls statuses. `SendOperation.result?.message_id` is available.
- `refreshLoaded(messageID)` refreshes local managed-channel history and matches a real message by ID. The remote channel ID is `channel.id`; the route `channelId` is local.
- `ChannelMessageComposer.onSubmit()` resolves after acceptance, then the composer clears text/file; a rejected request retains the draft.
- `sendIntent` currently holds an idempotency key across uncertain acceptance until accepted; do not break this safety property.

### Dependencies and call paths

- Composer submit → pane `send()` → `sendChannelMessage()` → HTTP 202 → operation poll → `refreshLoaded(remoteMessageID)` → history hook merge.
- Poll operation state is currently represented both in `pendingSends` and `notice`/`sendError`; pending status rows are rendered after the composer, outside the timeline.
- Timeline scroll anchoring observes only `[data-message-id]` items; pending presentation should have its own identity and must not enter message pagination/sorting.
