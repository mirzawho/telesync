# Telesync v0.0.4 — Telegram channel permission resolution

## A. Metadata

Approved by the user on 2026-11-11 for implementation.

## B. Requirements

### Problem

The new Create Channel path receives a `rpc.ChannelInfo` with Telegram
permissions, but registration drops them. Consequently its immediate response
and idempotent replay reconstruct the channel with all four permissions false.

### Desired behavior

- Preserve Telegram-resolved `new`, `edit`, `delete`, and `read` permissions
  from successful channel creation through local persistence, response, and
  replay.
- Keep unresolved rights unknown and mutations fail-closed; never infer rights
  from `is_managed`, the web administrator, or the fact of a create request.
- Keep Telegram capabilities separate from Telesync authorization.
- Continue using the selected connection's own worker/session for channel
  resolution and operations.

### Acceptance criteria

- [x] Create response preserves all four authoritative permissions.
- [x] Registered snapshot and idempotent replay preserve known permissions.
- [x] Unknown permission data remains unknown/fail-closed (existing local unknown
      snapshot behavior unchanged; successful create worker supplies a complete,
      non-min channel result).
- [x] Creator/admin/member/restricted role mapping remains correct and shared;
      creator source mapping has a gotd-level regression test.
- [x] Frontend uses the returned permissions and refreshes the created channel
  without reusing a different channel/connection's state.
- [x] Application authorization remains independently enforced; authorization
      code was not changed.
- [x] Tests and requested Go checks pass; live verification claims are
  limited to what was actually run.

### Out of scope

- Hardcoding capabilities, relaxing Telesync authorization, changing Send/Edit/
  Delete contracts, recreating or modifying the reported Telegram channel,
  resetting the database, deploying, committing, or pushing.

### Symbols and contracts

- `tgapi.NormalizePermissions(ChannelAccess) Permissions` is the one
  Telegram-capability calculation. Its existing tests already show that creator
  detection does not depend on admin-rights being present, provided upstream
  sets `Creator` and membership is known.
- `gotdclient.channelAccess(*tg.Channel, Membership)` takes `Creator` from the
  channel constructor separately; admin rights only set `Admin` and the three
  individual rights.
- `gateway.createChannel` currently discards the returned `info.Permissions`
  during `Channels.Upsert`; `writeCreatedChannel` later has only stored fields
  and therefore cannot return them.
- Channel list/detail JSON mapping copies RPC booleans without recalculating
  them. Local-detail responses intentionally use stored data, not Telegram.

### Dependencies and call paths

- Create: selected key → gateway worker assertion → worker RPC → that worker's
  `Manager.CreateBroadcastChannel` → `Self` and `channels.createChannel` on the
  same gotd client → channel extraction and normalizer → RPC result → gateway
  local upsert → create response / replay.
- Live detail: URL client key → matching worker → resolve current channel,
  best-effort `channels.getFullChannel` enrichment → normalizer → RPC → gateway
  channel view.
- Local detail: local row → stored permissions snapshot → public JSON. It does
  not refresh from Telegram.
- Telegram capabilities are not Telesync permissions. The gateway's existing
  resource visibility/authorization checks remain authoritative for API access.

## D. Implementation plan

1. **`internal/gateway/channel_creation.go`** — persist the permissions supplied
   by the worker as known only when they are genuinely authoritative; expose
   them in the first response and `writeCreatedChannel` replay. Do not synthesize
   rights when unavailable. If the RPC contract needs a known/unavailable bit,
   add it backward-compatibly across RPC/worker/gateway instead of treating
   zero-value booleans as an authoritative denial.
2. **`internal/gateway/channel_creation_test.go`** — retain the Red assertions
   added here; extend with unknown-rights, replay, and partial-success semantics.
3. **`internal/gotdclient` + `internal/tgapi` tests** — only if evidence requires:
   test generated `tg.Channel` creator flag without admin rights, participant
   creator/admin/restricted mapping, and ensure any full refresh uses the same
   `Manager`/connection. Reuse the existing shared normalizer; don't duplicate
   calculations.
4. **Frontend** — inspect create route/dialog identity and invalidation. Update
   only if current dirty implementation does not select/refetch the newly
   created channel with the correct keyed detail. Add tests for cache identity,
   permission refresh, and fail-closed loading if a change is required.
5. Run focused tests, then `gofmt`, `go vet ./...`, `go test ./... -count=1`,
   `go build -o ./bin/telesync ./cmd/telesync`, and frontend typecheck/tests only
   if frontend code changes. Do not claim live verification without a real
   configured session.
