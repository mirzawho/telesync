# Integrate channel message send, edit and delete UI

## A. Metadata

Preparation followed `.agents/workflows/prepare-change.md`. Implementation
requires a later explicit user instruction naming this handoff. The worktree
already contains numerous unrelated/uncommitted Go backend, API docs, memory,

## B. Requirements

### Problem

The active channel timeline currently renders messages and publishing actions,
but no direct composer or message edit/delete actions. The backend send, edit,
and delete routes exist in the shared worktree. Caption-only editing of a
message with media is currently unsafe: the PUT full-replacement parser treats
an absent `media` field as no replacement media, and the edit handoff explicitly
records that no keep-existing mode exists.

### Desired behavior

- Integrate direct text/media sending into the existing pane, with status polling
  and no success claim on HTTP 202.
- Use selected-channel `client_key` and `ChannelDetail.id` (Telegram ID) for all
  mutations; keep the local ID only for local history, permissions and routing.
- Resolve write visibility independently from the actual channel `permissions`
  object. Missing/unresolved capabilities never grant access.
- Add contextual per-message edit/delete controls, preserving publishing,
  reactions, views, timestamps, media and timeline scrolling.
- Edit/delete only after server confirmation; preserve message ID, avoid
  duplicate optimistic messages, and handle unknown operation outcomes safely.
- Support existing media keep/replace/remove semantics explicitly. Never send a
  caption-only edit that can remove the old media unintentionally.
- Abort/ignore stale requests and polling when channel identity changes.

### Acceptance criteria

- [ ] `permissions.new/edit/delete` independently gate corresponding controls.
- [ ] Unresolved identity/permissions never permit a mutation; backend 403 is
  surfaced honestly.
- [ ] Send supports JSON or one multipart file with native `photo`, `video`,
  `audio`, `voice`, and `document` kinds, operation polling, idempotency and
  confirmed reconciliation.
- [ ] Edit supports text, explicit media retention/replacement/removal and
  operation polling without changing the message ID or dropping media.
- [ ] Delete requires Persian destructive confirmation, uses one-message DELETE,
  and removes the item only after confirmed response.
- [ ] Existing pane, physical-left RTL bubbles, publishing, infinite paging,
  newest-follow and scroll anchoring remain intact.
- [ ] Focused tests, web typecheck and production build pass; live remote
  Telegram/Cat actions are not claimed absent authorized verification.

### Out of scope

- Redesigning the channel explorer or message bubble/publishing UI.
- Bulk operations, albums, scheduling, WebSockets, new dependencies or a second
  message viewer.
- Any live Telegram/Cat mutation without explicit authorization.

### Symbols and contracts

- `loadChannel()` maps the local URL ID to `data.channel.id` (Telegram ID) and
  `data.client_key`; the route passes both, plus the local ID, to the pane.
- `ChannelMessagesPane` calls `useMessageTimeline(channelId)` with local ID and
  must continue doing so for the existing local history route.
- `ChannelPermissions` booleans are optional at runtime; the UI capability
  resolver grants only on explicit `true`.
- `apiRequest()` builds `${BASE_URL}api/v1` and callers provide relative paths
  such as `/telegram/${key}/channels/${remoteID}/...`; it accepts JSON and
  FormData, preserving auth/cancellation and leaving multipart boundaries to
  the browser.
- Send operation states in handler: accepted status plus statuses `queued`,
  `processing`, `retrying`, `sent`, `failed`, `unknown`; `result.message_id` is
  authoritative only for `sent`.
- Edit operation states in handler: `queued`, `processing`, `retrying`,
  `edited`, `failed`, `unknown`; edited result retains target `message_id`.
- Send payload fields are text, entities, media `{kind}`, options; multipart
  fields are `payload` and one `file`. The parser/stager owns actual byte limit;
  no public per-connection limit was found, so do not invent a client limit.
- Edit text/media replacement uses the same payload. `keep_media: true` is an
  explicit edit-only mode, mutually exclusive with replacement `media`/`file`;
  omitting it retains historical full-replacement behavior. Execution confirms
  the same media descriptor on same-ID readback.
- Delete response reports `{deleted, connection.client_key, channel_id,
  message_id}` after remote confirmation.

### Dependencies and call paths

- route local ID → `loadChannel` record → `ChannelDetail.id` + `client_key` →
  active pane; history remains local ID → `/local/channels/{localId}/messages`.
- mutation → shared authenticated `apiRequest` → `/telegram/{client_key}/channels/{telegram_id}/...`.
- send 202 → status endpoint polling → confirmed message ID → refresh newest
  local history range, deduplicate and follow only if already near bottom.
- edit 202 → edit status poll → confirmed same message ID → update/invalidate
  existing timeline item without changing its position.
- delete request → confirmed `deleted:true` → remove only that message while
  preserving the reader's scroll anchor.

## D. Implementation plan

1. **`web/apps/web/app/lib/api.ts` and new typed API module/tests** — add
   authenticated JSON/multipart handling, typed send/edit/delete/status calls,
   cancellation and consistent errors; test URL/BasePath, payload, headers and
   FormData boundary behavior.
2. **Backend retention contract and tests, only as required** — add explicit
   keep-existing-media mode to the PUT replacement payload and worker operation
   using the existing source media; preserve current omitted/null semantics and
   verify text/entity edit does not remove/repost media. This change must remain
   minimal and must not touch other API architecture.
3. **Dedicated composer/attachment components + tests** — compact pane-bottom
   composer, one attachment, explicit kind selector including voice, safe
   validation/preview, Enter/IME behavior and stable idempotency per intent.
4. **Dedicated edit components + tests** — full replacement state, keep/replace/
   explicitly remove media, retain draft on failures, 202 polling and no
   optimistic confirmed content.
5. **Dedicated actions/delete components + tests** — permission-filtered
   accessible menu and Persian AlertDialog; no removal before confirmed result.
6. **`channel-messages.tsx`** — resolve and guard selected key, Telegram ID and
   channel permissions; ensure missing identity/capability fails closed.
7. **`channel-messages-pane.tsx`, `message-item.tsx`, timeline hook/pure module**
   — integrate components without changing published bubble/layout; protect
   async channel switches; reconcile mutations while preserving scroll and
   infinite-page history.
8. Add focused cross-feature permission, destination identity, 403, operation
   lifecycle, media-retention and channel-switch tests; verify mobile/RTL and
   existing viewer regressions.
