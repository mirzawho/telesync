# Resolve local channel permissions live

## A. Metadata

New focused behavior change. Explicit user approval was given on 2026-11-11.

## B. Requirements

### Problem

`GET /api/v1/local/channels/{localID}` currently builds the canonical response
from the SQLite snapshot and never asks the worker. Existing rows with unknown
or stale permission columns therefore return outdated booleans. Decision D58
currently states that local detail reads the snapshot; this task changes that
permission-source rule while preserving the rest of the local detail contract.

### Desired behavior

- After authenticating and authorizing the local row, fetch current channel
  information through the worker named by that row's `ClientKey`, using its
  remote `ChannelID` (not the local path ID).
- Return stored detail metadata with the successful live Telegram permissions
  replacing only the persisted permission snapshot.
- Bound the worker call with the gateway request timeout. Do not fetch history,
  avatar, media, participants, or write to SQLite.
- If the worker cannot establish current state, return an error (not HTTP 200
  with stale/unknown all-false permission values); retain existing failure
  classification and do not fall back to another connection.
- Keep Telesync authorization independent and fail-closed.

### Acceptance criteria

- [ ] A registered local row with unknown/all-false snapshot returns current
      worker capabilities in Local Channel Detail.
- [ ] The worker receives the stored remote ID through the stored client key;
      same numeric remote IDs on other connections do not cross-contaminate.
- [ ] Only permissions are replaced; the local response's other metadata and
      ID/shape remain compatible.
- [ ] Worker resolution errors return non-200 and never masquerade as denials.
- [ ] Repeated GETs use fresh role data (including promotion/demotion) and do
      not mutate persisted permission state.
- [ ] Existing application visibility checks remain before worker access.
- [ ] Existing live/detail and channel-list contracts remain intact.
- [ ] Focused and relevant Go tests, vet and build pass. Live verification claims
      are limited to what is actually available.

### Out of scope

- Repeating the creation persistence fix, refreshing SQLite, introducing a
  permission cache/background worker, changing the API response shape, adding a
  public endpoint, changing message Send/Edit/Delete authorization/contracts,
  frontend redesign, channel mutation, deployment, commit, or push.

### Symbols and contracts

- `getLocalChannel(w, r, localID, requestID)` calls `requireLocalChannel`
  first, preserving 404/403 visibility checks. The returned `channelstore.Channel`
  carries both `ClientKey` and Telegram `ChannelID`.
- `Worker.Channel(ctx, rpc.ChannelRef{ChannelID: ch.ChannelID})` is the existing
  single worker operation for fresh channel state; `channel()` uses it for live
  detail. `ChannelRef` carries the remote ID, not the local row ID.
- `workerFor` returns only the matching keyed worker, 404 for an unconfigured
  client, and 503 when the registry is unavailable; there is no fallback.
- `localChannelDetail` makes the canonical local response from persisted
  metadata. A minimal implementation can replace only its `Permissions` with
  the worker's returned `ChannelInfo.Permissions` before serialization.
- Worker errors can be passed through `upstreamError`, which distinguishes
  unavailable (503), timeout (504), channel not found (404), and other failures.

### Dependencies and call paths

- Local detail: authenticate → parse local ID → `requireLocalChannel` (store
  load, then `visible(..., ActionView, localID)`) → `workerFor(ch.ClientKey)` →
  `Worker.Channel(remote ch.ChannelID)` → existing worker/MTProto resolver and
  shared normalizer → overlay live permission booleans on local detail view →
  JSON response.
- Existing live detail already follows URL key → that worker → `Worker.Channel`
  → channel view. Reuse this seam; no nested HTTP, extra connection, or duplicate
  normalizer.
- GET must not call `Upsert` or any write method. The real store uses SQLite;
  fake worker registry enables connection isolation tests.
