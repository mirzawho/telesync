# Add the Telegram channel message deletion API

## A. Metadata

Preparation followed `.agents/workflows/prepare-change.md`; the user approved
this named handoff, and implementation is underway. The user request is in the pasted text attachment and asks
for `DELETE /api/v1/telegram/{key}/channels/{id}/messages/{message_id}` to
delete one remote Telegram/Cat channel message through the selected worker.

## B. Requirements

### Problem

The requested channel-message DELETE route is absent. A request at that path is
currently handled by the generic read-only Telegram route and answers `405`.
There is no deletion operation in the gateway Worker contract, worker RPC
Backend contract, worker Telegram interface, or gotd adapter.

### Desired behavior

- Authenticate the caller and resolve only the configured worker named by
  `{key}`.
- Parse a positive supported channel id and one positive MTProto message id
  without overflow or truncation.
- Resolve the channel using that worker's own peer data and access hash.
- Require application channel delete authorization on the local
  `managed_channels.id`, with the existing view requirement and deny-by-default
  behavior. Let Telegram remain authoritative for its own restrictions.
- Confirm the target exists in that same channel/connection before deletion if
  required to interpret `channels.deleteMessages`'s affected-message result;
  invoke the channel-scoped method with exactly one message id.
- Return `200` with `deleted: true` only after the remote call succeeds. Keep
  the standard envelope and do not return raw MTProto structures.
- Map not-found, authorization, flood-wait, worker-unavailable and ambiguous
  timeout outcomes using existing API/RPC conventions where possible.
- Keep reads and media access aligned with remote state after success. Do not
  remove local data before remote confirmation or erase automation history.
- Document the route in the existing source documentation and regenerate
  generated API pages with the documentation tool.

### Acceptance criteria

- [ ] The exact DELETE route is registered; other methods are refused with
  `Allow: DELETE`.
- [ ] Invalid, zero, negative and overflowing ids are rejected as `400`.
- [ ] Authentication is required; view-only and out-of-scope callers cannot
  delete, while an authorized caller can reach the operation.
- [ ] Only the worker selected by `{key}` is called, with that worker's resolved
  channel and exactly one message id.
- [ ] The implementation invokes `channels.deleteMessages`, never a channel or
  history deletion method.
- [ ] Remote confirmation is required for `deleted: true`; repeat deletion and
  typed Telegram failures have documented, honest outcomes.
- [ ] Existing reads, media, direct send, source-based publishing and workflow
  publishing retain their behavior.
- [ ] API source docs and generated docs pass the repository check.
- [ ] Focused tests and required regression/static checks pass. Live Telegram
  verification is reported separately and is not claimed without credentials
  and an authorized test channel.

### Out of scope

- Editing or bulk deletion.
- Channel/history deletion, a deletion queue, new idempotency tables, frontend
  redesign, direct-send changes, publishing/workflow changes, new SDKs,
  deployment, commit or push.

### Symbols and contracts

- `Server.serveTelegram` authenticates before revealing whether a worker key is
  configured; the selected worker remains the only worker for that request.
- `Server.routeTelegram` currently treats channel messages as GET-only except
  the dedicated `send` route.
- `gateway.Worker`, `rpc.Backend`, `worker.Telegram`, `rpc.Client` and
  `rpc.NewHandler` are the end-to-end seams that need one synchronous delete
  operation. The private worker operation is scoped to the already-selected
  worker; the gateway supplies the channel id and message id.
- `worker.Service.channelByID` obtains the `tgapi.Channel` (including the
  access hash) from its own client's dialogs. `gotdclient.Manager` receives
  that resolved channel, so it can construct the complete `InputChannel`.
- `gateway.targetOf(ctx, key, telegramID)` resolves the local
  `managed_channels.id`. `visible(auth, KindChannel, ActionDelete, localID)`
  is the existing app permission rule; `content.publish` is not a delete
  permission.
- `rpc.CodeNotFound`, `rpc.CodeSendForbidden`, `rpc.CodeRateLimited`, gateway
  error mapping, and bounded request contexts are existing conventions to
  reuse where their meaning matches. The request timeout means an MTProto
  timeout can leave a genuinely unknown remote outcome; do not retry or claim
  confirmation automatically.
- Individual message bodies are served from the selected Telegram worker.
  Local channel storage holds channel snapshots/permissions, not message-body
  rows. Automation/event and publication history is separate and must remain.

### Dependencies and call paths

- Current read: HTTP → gateway route → selected `Worker.Message` → worker
  `channelByID` → selected Telegram client `Message` →
  `ChannelsGetMessages` using `InputChannel`.
- Current send: HTTP → async `Server.sendTelegramMessage` → staging/operation
  queue. It is intentionally a different contract and must not be changed.
- Proposed delete: HTTP auth/key resolution → local row + `ActionDelete` and
  view authorization → gateway `Worker.DeleteChannelMessage` → private RPC
  → worker `Service.DeleteChannelMessage` → that worker's resolved channel →
  gotd `ChannelsDeleteMessages` with one id → remote result → HTTP envelope.

### Unknowns / risks

- Verify the installed gotd generated request/result types and exact
  `channels.deleteMessages` error behavior before choosing conversion/range
  checks. Affected update counters are not a count of deleted ids.
- Establish how `MSG_ID_INVALID` and its race with a preflight lookup should map
  to not-found without converting arbitrary failures into success. Proposed
  behavior is an exact same-connection message preflight, then 404 when the
  exact item is confirmed absent; never infer success from a generic invalid-id
  error.
- Telegram's `permissions.delete` is a snapshot capability, while Telegram is
  the authority for whether this account can delete this particular message
  (for example, its own post). Do not gate solely on stale local metadata; map
  typed server refusals safely.
- Confirm whether any worker cursor/cache needs invalidation. Existing message
  reads are remote and the worker cursor is pagination state, not cached
  message content; future media reads also go back to Telegram.
- The message id must fit the actual generated MTProto field without
  truncation; verify the project's gotd version before selecting `int32` or
  other exact boundary.
- Live test credentials/channel are not provided. Do not perform destructive
  actions on a production channel.

## D. Implementation plan

1. **`internal/gateway` tests** — keep the new HTTP contract test and add focused
   authorization/isolation/error cases using real account/store fixtures and
   fake workers. Extend the fake worker only with the eventual RPC method.
2. **`internal/rpc`** — define a minimal request/result or empty success
   contract, add the backend handler and client method, and add socket roundtrip,
   error mapping, and method tests. Keep the private operation synchronous.
3. **`internal/tgapi`, `internal/worker`** — add a narrow Telegram delete seam;
   require worker authorization and resolve the target from that worker's own
   channel/dialog before invoking the adapter. Test not-found and typed failures.
4. **`internal/gotdclient`** — use the generated `ChannelsDeleteMessages`
   method with a fully resolved `InputChannel` and one message id. Preflight the
   exact channel/message only if needed to distinguish absence; test the actual
   method/request using the in-memory `tgtest.Server`, including the selected
   access hash, single id and forbidden/invalid/flood errors. Assert no history
   or channel deletion method is invoked.
5. **`internal/gateway`** — register DELETE before the read-only message arm;
   validate path ids, resolve app permission by local channel row and selected
   key, synchronously await RPC within `RequestTimeout`, map errors without
   leaking backend details, emit safe structured result logs, and return the
   confirmed standard envelope.
6. **Tests** — verify route success and wrong methods; message-id boundaries;
   no/invalid auth; allowed/delete-denied/view-only/out-of-scope users; same
