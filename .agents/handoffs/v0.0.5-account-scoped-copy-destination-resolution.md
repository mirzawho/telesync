# Fix account-scoped copy destination resolution

## A. Metadata

Preparation only. Production code has not been changed. The user must explicitly
approve this handoff by name before implementation.

## B. Requirements

### Problem

Account-scoped copy can reject an accessible destination when a channel with the
same remote Telegram ID is locally registered under another account on the same
server. The discovered remote peer and the selected account are valid, but the
copy resolver performs a server-key-scoped local lookup first.

### Desired behavior

- Resolve a destination using the selected account identity and remote peer ID,
  never a global/server-key-only channel lookup.
- For an account-owned local registration, apply local visibility to that
  selected account's row. For an accessible but unregistered peer, do not require
  a managed-channel registration; revalidate access and sending permission
  through the selected account's Runner.
- Preserve account ownership, application visibility, Telegram `Permissions.New`,
  source-local-channel resolution, media handling, and idempotency.
- Never switch accounts or use a shared/server-level Runner as fallback.
- Keep remote `channel_id` separate from local `managed_channels.id`.

### Acceptance criteria

- [x] The regression in §F passes: selected account B can copy to peer 5002 even
  though another account's local registration uses that same peer ID.
- [ ] Same peer ID on distinct accounts and network identities resolves only
  within the selected account.
- [x] Unregistered discovered destination can publish when the selected Runner
  confirms access and `Permissions.New`.
- [x] Inaccessible and non-sendable peers are rejected precisely; no alternate
  Runner is called.
- [x] Source account remains independently resolved; cross-account source and
  destination copying works when both are authorized.
- [x] Cross-user account use remains denied before Runner execution.
- [x] Preserved media lookup remains tied to the source message/account.
- [x] Idempotency does not duplicate a completed publication and cannot collide
  across selected accounts.
- [ ] Focused Go tests, frontend tests/typecheck/build, vet, full Go suite/build,
  and docs checks (if contracts change) are recorded honestly.
- [ ] Live HTTP/daemon verification is performed only with an authorized test
  destination; otherwise marked unverified.

### Out of scope

- Removing account ownership or permission validation.
- Automatically registering a destination for monitoring.
- Rewriting the publishing engine or changing text/entity/media contracts.
- Changing account login, Runner lifecycle, unrelated APIs, or dialog design.
- Database reset, commit, push, or deployment.

### Symbols and contracts

- `Service.resolvePublishDestination(ctx, actor, key, accountID, destID)`:
  current conflicting branch at `resolve.go:142-151` calls
  `Channels.Get(ctx, key, destID)` and returns HTTP 409 when that row's
  `AccountID` differs.
- `Store.Get(ctx, clientKey, channelID)` identifies a row by server key and
  remote ID; it is not sufficient to identify a personal-account destination.
- `Store.GetForAccount(ctx, accountID, channelID)` has account-scoped SQL
  semantics and returns only that account's registration.
- The selected destination worker is subsequently resolved with
  `publishWorker(accountID)` and its `Channel` result is checked for
  `Permissions.New`.
- Account-scoped route dispatch resolves ownership before invoking the shared
  publish route.

### Dependencies and call paths

- Selected account URL → gateway account ownership resolution → account worker
  dispatch → publishing pipeline → `resolvePublishSource` via source local row →
  `resolvePublishDestination` → destination `Channel` permission check → send.
- Account-scoped discovery → selected account worker `Channels` → real remote
  channel IDs and Telegram permissions. Discovery does not require local managed
  registrations.
- The observed rejection occurs in destination local-row lookup before the
  selected account Runner's `Channel` permission revalidation.

## J. Final notes

Implementation: account-scoped destination resolution now checks the selected
account's owner and uses `GetForAccount(accountID, remoteChannelID)` when
resolving local registrations. Another account's same-server registration is
not consulted. Unregistered peers continue with `localID == 0` and must pass
application visibility plus the selected worker's live `Channel` and
`Permissions.New` check. Legacy unscoped resolution retains the existing
server-key lookup.

Migration 23 scopes publish-operation uniqueness by user, account, and
idempotency key. Existing rows are preserved; legacy Telegram operations are
bound only when the destination prefix unambiguously names an account owned by
that same user. Unresolved rows remain unbound. The publisher carries the
selected destination account into operation creation/replay. Tests cover
same-user/same-key operations across accounts, independent retries, migration
preservation, and source/destination account independence.

No frontend/API contract changes were needed: the dialog
already posts to `accountApi.messageCopy(accountID)` and the payload builder
uses the selected channel ID as the remote `destination.channel_id`, preserving
the source `local_channel_id`.
