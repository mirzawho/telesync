## B. Requirements

### Problem

The active channel explorer has a local Add/Join dialog and a per-row menu, but
no native Telegram channel creation, no username precheck, and no channel
information dialog. The current gateway accepts `GET /channels/{ref}` for
details and `POST /channels/{ref}/join` for the existing join/registration
workflow. Channel details already include the Telegram metadata needed for the
information dialog.

### Desired behavior

- Add exactly two public routes on the existing Telegram API namespace:
  `POST /api/v1/telegram/{key}/channels` and
  `GET /api/v1/telegram/{key}/channels/username-availability?username=...`.
- Create an actual broadcast channel only through the selected connection;
  assign public username and upload optional image through that same worker;
  record it using existing managed-channel persistence.
- Preserve honestly reported partial outcomes and avoid blind retries of a
  non-idempotent remote create. Support request idempotency and conflict on key
  reuse with different input.
- Username checking is an advisory precheck when resolution cannot prove
  assignability; the final assignment response is authoritative. Never create a
  temporary channel or fabricate an `InputChannel` to check a name.
- Replace the toolbar `+` with a vertical-more dropdown, Create and Join actions;
  route Create to `/admin/channels/new` and continue to use the existing join
  dialog/behavior.
- Add `اطلاعات کانال` to each authorized row's existing More menu and fetch the
  existing detail resource for that specific channel.
- Keep the channel explorer layout, search, categories, existing join/register
  semantics, message viewer and message routes unchanged.

### Acceptance criteria

- [x] The two exact public API routes are authenticated, selected-key scoped,
  authorized with `channels.create`, and included in generated API docs.
- [x] Create validation covers required title, description limits, visibility,
  username syntax and avatar limits/content type; backend remains authoritative.
- [x] Worker/gotd executes `channels.createChannel` with broadcast true and
  megagroup false, extracts the created channel robustly, assigns username only
  for Public, and uploads an image as a chat photo when provided.
- [x] Public username final assignment is authoritative; advisory `unclaimed`
  is not represented as guaranteed assignability.
- [x] Durable idempotency/recovery prevents same-key duplicate creation and
  distinguishes unknown remote outcome; partial setup returns real remote ID
  and completed/failed steps without deleting the remote channel.
- [x] Successful remote create is registered locally and response carries the
  local managed ID separately from Telegram ID.
- [x] Menu actions are permission gated; Search and Join behavior remain intact.
- [x] Dedicated responsive RTL Create page implements server/title/description,
  optional avatar, Private default, Public username debounce/cancellation and
  accurate partial-success navigation.
- [x] Existing per-row actions remain; Information dialog shows only actual
  detail fields and does not reveal access hashes or worker secrets.
- [x] Focused behavior tests pass, then relevant Go/frontend suites, API docs
  checks and production builds pass. Browser/live verification is reported only
  if actually performed.

### Out of scope

- Choosing or editing the numeric Telegram channel ID.
- Replacing/rebuilding the existing Join flow or claiming local registration
  means remote membership where it does not.
- Group/supergroup creation, channel deletion, ownership transfer, unrelated
  message viewer changes, third public API, new UI framework or dependency.
- Live production Telegram/Cat channel creation without explicit authorization.

### Symbols and contracts

- `gateway.Worker` contains Find/Channel/Join and message operations but no
  create-channel or username-check operation yet.
- `ManagedStore.Upsert` persists a channel snapshot keyed by `(client_key,
  channel_id)`; join uses this and reports Telegram success/local storage failure
  honestly. Created channels should use that safe local registration seam.
- Existing `channelView.ID` is the Telegram channel ID string. Existing
  `/local/channels/{id}/messages` uses local `managed_channels.id`; creation
  response and UI routing must keep both namespaces explicit.
- Current `channels/{ref}` detail dispatch occupies the 3-segment channel GET
  path. The availability route has the same path depth, so it must be checked
  before the dynamic detail arm. Create is POST on the `channels` collection.
- `channels.create` is an existing global permission and is required to imply
  `channels.view`; channel message `permissions.new` is not a creation grant.
- Existing detail API already returns title, username, description, type, avatar
  availability, membership, managed status, notices and permission snapshot.
- `apiRequest()` sets `Content-Type: application/json` and JSON-stringifies any
  body today; multipart support must not manually set the browser multipart
  boundary.

### Dependencies and call paths

- HTTP `serveTelegram` authenticates and resolves exactly `{key}` worker → route
  and authorize → worker RPC → worker service → selected gotd manager → Telegram.
- Confirmed remote create → resolve actual returned channel/input peer → apply
  username/avatar setup sequentially → `ManagedStore.Upsert` → return remote ID
  and local row ID separately. Failure after create is partial, not total failure.
- Username GET → normalize/validate → selected worker resolution check → status
  occupied/unclaimed/invalid/unknown. No invented input peer or temporary create.
- Frontend server change aborts/invalidate username check; debounce response is
  guarded against stale username/key. Successful create invalidates/reloads
  channels and navigates using local ID.
- Per-row Information → selected row's `client_key` + Telegram ID → existing
  `/telegram/{key}/channels/{telegramID}` detail API, with stale request
  cancellation on row switch.
