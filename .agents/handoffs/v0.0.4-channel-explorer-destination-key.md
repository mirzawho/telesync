# Supply the mapped Telegram client key to Channel Explorer detail

## A. Metadata

Focused API/UI integration fix. Explicit user approval was given on 2026-11-11.

## B. Requirements

### Problem

For `/admin/channels/2/messages`, the nested channel detail response carries
`data.channel.id` (`"98"`) and current channel permissions, but omits the
connection identity. The route's existing `loadChannel` reads `data.client_key`
and defaults it to `""`. `ChannelMessagesPane` then defines
`identityValid = Boolean(client.trim()) && remoteIDValid`; an empty key makes it
false even when remote ID `98` and all four permissions are valid. Consequently
`writable`/`editable`/`deletable` are all false and line 820 renders
`مقصد یا مجوز کانال در دسترس نیست.`. Permission parsing itself is correct:
`apiRequest` unwraps envelope `.data`, the route reads `.channel`, and
`channelMessageCapabilities` reads `channel.permissions.{read,new,edit,delete}`.

### Desired behavior

- `GET /api/v1/local/channels/{id}` includes the persisted local record's
  authoritative `client_key` as additive sibling `data.client_key`, without
  putting connection identity into the canonical `data.channel` object.
- For local channel 2, the existing route reads `data.client_key`, keeps
  `channel.id` (remote ID 98), and passes both values to the message pane.
- With a non-empty mapped key and explicit true permissions, identity is valid;
  read, send, edit, and delete remain independent capabilities and the false
  destination/permission warning is absent.
- Missing/invalid destination remains distinguishable from a confirmed denied
  Send capability. Failed detail requests continue using the route's existing
  unavailable/error state and retry, not false permissions.
- Never infer client identity from username, title, category, server filter, or
  first/selected server; use `ch.ClientKey` from the authorized local mapping.
- Keep current message API URLs keyed by that connection and the remote channel
  ID, preserve Telesync authorization, and make no message operation on load.

### Acceptance criteria

- [ ] Exact UI root cause is the empty `clientKey` caused by absent
      `data.client_key`; not permissions parsing or stale cache.
- [x] Local detail adds `data.client_key` from the row's authoritative mapping.
- [x] Local path ID 2 remains distinct from Telegram ID 98.
- [x] The route uses key `cat` (or whatever the stored row actually names) and
      remote ID `98`, not filter selection or username inference.
- [x] Existing all-true permissions with valid identity render the composer and
      do not render the unavailable warning.
- [x] Read-only / send-only / edit / delete capability checks remain independent.
- [x] Missing identity and API load failure are not described as confirmed
      permission denial.
- [x] Focused Go and panel regressions, web typecheck and production build pass.
- [x] Running-app verification is claimed only if active frontend/binary and
      authenticated browser access are available.

### Out of scope

- Reworking Telegram permission resolution, message Send/Edit/Delete APIs,
  server/category filters, UI redesign, channel mutations, caching frameworks,
  deployment, commit, or push.

### Symbols and contracts

- `clientLoader` → `loadChannel(token, localID, url)` requests
  `GET /local/channels/{localID}`. A successful payload is envelope-unwrapped by
  `apiRequest`; route code reads `{ channel, client_key }` from `data`.
- `ChannelMessagesPane(channel, channelId, client)` expects `channelId` to be the
  local row ID and `channel.id` to be the Telegram ID. Message routes use
  `client` plus `channel.id`.
- `channelMessageCapabilities` is already strict and independent:
  `read`, `new`→`create`, `edit`, `delete` each map separately.
- Gateway `getLocalChannel` runs `requireLocalChannel` first (Telesync resource
  view authorization), then the keyed live worker call from the previous
  approved fix. Adding `client_key` must use the same loaded local row; no new
  lookup or permission bypass is required.

### Dependencies and call paths

- Browser route local ID → authenticated client loader →
  `apiRequest(GET /local/channels/{localID})` → envelope `data` → currently
  `channel` plus absent `client_key` → `clientKey=""` → pane sees valid remote ID
  and true permissions but `identityValid=false` → all management controls are
  suppressed and line 820 shows the generic warning.
- Corrected: gateway row lookup/authorization → `data.client_key=ch.ClientKey`
  and `data.channel` unchanged → existing loader passes key and remote ID 98 →
  existing independent permission gates expose permitted controls.
- Parent Channel Explorer already loads `/local/channels` records (including
  `client_key`), but the detail child does not consume parent loader data. The
  existing child loader explicitly expects `data.client_key`; a small additive
  field on the existing detail envelope avoids filter-dependent identity or a
  duplicate list fetch.
