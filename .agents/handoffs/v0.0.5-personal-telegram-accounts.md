## B. Requirements

### Problem

Telesync v0.0.4 authenticates Telegram/Cat **centrally**. `appconfig.Config.Clients`
is a list of configured instances (`internal/appconfig/config.go:202`), each with
one `Key` (`official`, `cat`), one `APIHash`, one `Phone`, one `SessionPath` and
one `RPCSocketPath`. `runtime.Registry` maps `clientKey → worker`
(`internal/runtime/runtime.go:31`), and `gateway.Registry.Worker(key)` routes
every Telegram call (`internal/gateway/gateway.go:65`).

Consequences: several application users act through **one** Telegram identity;
access is granted by assigning users to a shared connection; sessions are
plaintext per-client JSON files (`internal/sessionstore`, 0600/0700 but **not
encrypted**); `managed_channels` is keyed on `client_key` + `channel_id` so two
users cannot independently register the same remote channel; update state,
peer caches and jobs have no owner dimension.

### Desired behavior

- Every Telesync user connects and authenticates **their own** Telegram/Cat
  account(s) through the panel — phone/code, 2FA, and QR where supported.
- Multiple accounts per user, across servers. Sessions independent; one user's
  session is never used for another user's operation.
- Sessions encrypted at rest (AES-256-GCM, account-bound AAD), survive restart
  with no new OTP.
- Workers, RPC routing, update state, peer caches, channels, messages, media,
  webhooks, workflows and background jobs all owner/account-scoped.
- Server definitions (`official`, `cat`) stay global and admin-managed.
- Shared Telegram access-assignment retired in backend **and** UI.
- Categories, WordPress sites, user/role administration preserved unchanged.
- Legacy central sessions quarantined; adoption explicit and auditable.

### Acceptance criteria

- [ ] `telegram_accounts` exists; every account has an explicit owner and an opaque stable id
- [ ] Sessions sealed AES-256-GCM at rest; wrong account context cannot open another's
- [ ] Phone/code login works; 2FA works; QR works where supported (else explicit unsupported)
- [ ] Login attempts are a persisted, owner-scoped, expiring state machine
- [ ] Sessions restored after restart without a new OTP
- [ ] Workers are account-scoped; RPC routing is account-scoped
- [ ] Update recovery is account-scoped; no shared `pts`
- [ ] `managed_channels` uniqueness is `(account_id, channel_id)`; two users may hold the same remote channel separately
- [ ] Send/edit/delete resolve the correct owner account
- [ ] Webhooks, workflows, jobs carry owner/account identity; history is owner-private
- [ ] Event dedup is source/account-scoped — no cross-user suppression
- [ ] Shared Telegram access-assignment UI **and** authorization removed
- [ ] Categories, WordPress sites, admin management still functional
- [ ] Two-user isolation test matrix passes (§37 of the brief)
- [ ] Reconnect/restart/crash-recovery tests pass
- [ ] Legacy sessions quarantined or explicitly adopted; ownerless jobs paused
- [ ] `gofmt`, `go vet`, `go test ./...`, `go build`, docsgen `--check`, apidocs, web typecheck all pass

### Out of scope

- No live Telegram/Cat verification (this checkout has no credentials and none
  may be invented). Mocked/simulated integration is reported as simulated.
- No WordPress subsystem redesign; no category redesign.
- No replacement of gotd/td. No new external infrastructure.
- No commit, no push, no deployment.

- `gateway.Registry.Worker(key string) (Worker, bool)` — **the** routing seam.
  Its key becomes `account_id`.
- `sessionstore.NewAt(path) (*Store, error)` — `session.Storage` for one file.

  a persisted HTTP state machine, not wrapped.

- HTTP route → `serveTelegram` resolves `{key}` → `registry.Worker(key)` →
  `rpc` client → worker socket → `gotdclient` → MTProto.
- `cmd/telesync` → `runtime.RunDaemon` → supervisor (worker processes) + gateway.
- Automation: `profile.UpdateHandler` → worker observes → private `automation.sock`
  → daemon persists event → durable queue → webhooks / workflows.

### Unknowns / risks

- **Cat QR support is unverified.** Contract requires hiding QR when unsupported;
  whether the custom backend supports QR is an unknown to report, not guess.

  nullable `created_by`. The brief forbids inventing ownership → quarantine.
- **Live MTProto behavior unverifiable** here (no credentials). All auth tests

- **Supervisor runs worker *processes*.** Per-account workers multiply processes;
  `TELESYNC_ACCOUNT_MAX_WORKERS` bounds this, but process-vs-goroutine for
  accounts is an owner decision if the supervisor proves too heavy.
- `managed_channels` rebuild must preserve `id` values exactly — several FKs

  depend on them. A silent id remap would be a data-loss bug.
