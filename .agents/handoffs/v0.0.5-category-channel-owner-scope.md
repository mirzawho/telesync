# Category channel owner scope

## A. Metadata

See frontmatter. The gateway implementation is not started. `categories.go`
already has unrelated dirty request-decoder changes; preserve them.

## B. Requirements

### Problem

`GET /api/v1/local/categories/{id}/channels` currently obtains all registered
rows through `CategoryChannels(categoryID)` and then filters using application
permissions. With global category/channel view grants, duplicate registrations
of the same remote Telegram channel under different users are both visible.
The fixed operator token also has broad permissions but no Telesync owner.

### Desired behavior

- Category metadata/permissions remain global and unchanged.
- The member query is scoped to the authenticated Telesync principal's
  `ownerUserID`; no owner (including the operator token) cannot enumerate
  another user's Telegram registrations.
- Preserve the existing channel visibility check after owner scoping.
- Use Agent A's exact store contract:
  `CategoryChannelsForOwner(ctx, ownerUserID, categoryID)`.
- Avatar cache identity remains account-scoped: explicit account routes use
  `account_id`, and legacy keyed routes resolve the caller's exact account
  before cache access. Do not change Agent A's `channels.go` or avatarcache
  files.

### Acceptance criteria

- [ ] A direct HTTP test with duplicate remote registrations and global view
  grants returns only the authenticated owner's local registration.
- [ ] The operator token/no-owner case returns no private Telegram registrations.
- [ ] The category record and its data/permission behavior remain unchanged.
- [ ] Account-scoped avatar cache receives account ID; legacy keyed avatar
  requests use the exact resolved account ID before cache access.
- [ ] Focused gateway category and avatar-routing tests pass.

### Out of scope

- Do not edit `internal/channelstore` or frontend files.
- Do not change category records, schema, category permissions, or API docs.
- Do not edit Agent A's `internal/gateway/channels.go` or avatarcache files.

### Symbols and contracts

- `(*Server).listCategoryChannels` calls the `CategoryMembers` interface,
  filters returned rows using `visible(...KindChannel, ActionView, ch.ID)`,
  then renders the existing category-channel response.
- Required new interface method:
  `CategoryChannelsForOwner(ctx context.Context, ownerUserID, categoryID int64)`.
- `accountsResource` authenticates, resolves the named account, validates its
  channel registration, and dispatches with both `req.accountID` and
  `req.serverKey`.
- Current `routeTelegram` calls `s.avatar(..., serverKey, ...)`, while avatar
  cache uses that argument as the cache key. The right handoff between the
  route and Agent A's changed avatar signature is not yet agreed.

### Dependencies and call paths

- category member HTTP route → category authorization → owner-scoped store
  method → existing channel visibility filter → response.
- account route → resolve exact account/owner → `routeTelegram(accountID,
  serverKey, ...)` → avatar handler/cache (currently passed server key).
- legacy keyed route must resolve its exact account before any avatar cache
  read; do not fall back to a server-wide cache namespace.
