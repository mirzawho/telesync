# Fix account-scoped publishing destination channel listing

## A. Metadata

Approved implementation in progress.

## B. Requirements

### Problem

The Publish Message dialog requests
`GET /telegram/accounts/{account_id}/channels?page=1&per_page=100&capability=send`.
The canonical route reaches the account resource handler, which currently
returns generic 404 before channel discovery.

### Desired behavior

- Serve account-scoped channel listing at both `/api/v1/...` and mounted
  `/admin/api/v1/...` through the real registered gateway mux.
- Resolve the explicitly selected owned account and only its Runner.
- Return accessible Telegram dialogs with real remote peer IDs and account
  permissions; use `permissions.new` for `capability=send`.
- Preserve pagination, visibility, upstream error classification and publication
  account identity.
- Keep the existing publishing dialog and WordPress flow; add Persian retry and
  empty states, prevent stale account results/selections, and ensure pagination
  does not silently hide destinations.
- Final publication continues using the same selected account ID, selected peer
  IDs, source identity, edits and media configuration.

### Acceptance criteria

- [x] Mounted account channel-list route returns 200 and a paginated envelope.
- [x] Ownership and selected-account worker isolation are enforced.
- [x] Only channels Telegram reports as sendable pass `capability=send`.
- [x] Empty eligible results are HTTP 200 with an empty collection.
- [x] Switching accounts clears old destinations; stale responses are ignored.
- [x] Real request errors show Persian error/retry, not empty state or raw English.
- [x] Publishing uses the account that loaded the selected destinations.
- [ ] Focused/full backend and frontend checks, docs checks and builds pass; full Go suite has unrelated-looking but untriaged failures.
- [ ] Authorized live HTTP/browser verification is completed if available, else
  explicitly left unverified.

### Out of scope

- Rewriting personal-account authentication or Runner lifecycle.
- Global Telegram session/server-key fallbacks or automatic account selection.
- Unrelated schema/UI changes or WordPress publishing changes.

### Symbols and contracts

- `Server.accountsResource` authenticates/resolves the explicit account, then
  currently rejects fewer than three suffix segments.
- `Server.routeTelegram` supports `GET channels` for two route segments and calls
  `Server.channels`.
- `Server.channels` calls the selected worker's `Channels`, applies app
  visibility and capability filtering, and returns pagination metadata.
- `applyCapabilityFilter` maps `send` to `Permissions.New`.
- `Server.resolveAccount` and `accountScopedWorkers` enforce owner and account
  identity; no shared-session fallback.
- `PublishDialog` already requests the canonical account URL with
  `page=1&per_page=100&capability=send`, aborts/ignores stale requests and clears
  old channel list. It currently passes raw API English error messages and only
  requests the first page.
- `gotdclient.Manager.Dialogs` is the existing actual-dialog discovery source;
  destination discovery must not rely only on managed-channel rows.

### Dependencies and call paths

- `/admin/api/v1` → `ServeHTTP` → BasePath strip → `serveAPI` →
  `accountsResource` → `routeTelegram` → `channels` → selected account worker
  → visibility/capability filter/envelope.
- Dialog account choice → account-scoped GET → remote channel IDs → existing
  publish workspace with selected account ID and destination IDs.

## F. Red-phase evidence

- Command: `go test ./internal/gateway -run
  '^TestAccountScopedChannelListIsRegisteredOnMountedAdminMux$' -count=1`
- Exit code: `1`
- Failure:
  ```
  mounted account channel list status = 404; want 200,
  body={"error":{"code":"not_found","message":"The requested resource does not exist.",...}}
  ```
- Genuine Red: request passes through the registered gateway handler with a
  real SQLite-owned account, valid user token, account-specific worker fake and
  `/admin` BasePath. Actual route returns generic 404 before calling the worker.
- Exact root cause: `accountsResource` splits the collection suffix as
  `["{account_id}", "channels"]` (two segments), then rejects `len(segments) <
  3`. BasePath stripping works; the frontend URL matches; route is not missing
  or shadowed. This is a handler path-shape 404, not account-not-found or Runner
  failure.
- No environment/unrelated failure observed in this focused run.
